# Порядок выполнения плана

[Общий план](../PLAN.md). Назначение: надёжная работа небольшими шагами без постоянного повторения аудита.

## Минимальный контекст перед шагом

1. Прочитать действующие инструкции проекта, карточку продолжения в PLAN.md и только текущий этап.
2. Для изменений загрузчика, фабрики, конфигурации или публикации прочитать нужные разделы [COMPATIBILITY.md](COMPATIBILITY.md).
3. Проверить рабочие изменения. Не перезаписывать чужую работу и не очищать весь рабочий каталог.
4. Открыть файлы, перечисленные в текущем шаге, и соответствующий тест. Поиск начинать с rg/rg --files; независимые чтения объединять.
5. Если фактический код расходится с планом, записать конкретное расхождение и проверить его. Предыдущие измерения и номера строк не считать вечными.

История чата и все остальные этапы не нужны для каждого изменения. Обычно достаточно одного шага, контракта для него и нескольких исходников. Если задача действительно пересекает границы модулей, расширить чтение на эти зависимости.

## Цикл одного шага

1. Сформулировать наблюдаемый результат одним предложением: какой вход сейчас ломается и что должно получиться.
2. Для исправления кода добавить маленький регрессионный тест и убедиться, что он воспроизводит исходную ошибку. Для рефакторинга сначала должен проходить тест прежнего поведения.
3. Внести минимальную правку в одну область. Переименование, обновление зависимостей и изменение поведения не объединять без необходимости.
4. Запустить целевой тест. Если изменилась общая фабрика или загрузчик, дополнительно запустить минимальную проверку совместимости.
5. Просмотреть diff: результат соответствует задаче, публичный контракт сохранён, посторонних изменений нет.
6. Отметить шаг и записать команду, результат и оставшиеся ограничения. Продолжить следующий порученный шаг.

Один шаг допускается разделить на меньшие части с суффиксами, например S1.4a и S1.4b. Сначала указать, что проверяет каждая часть. Не объединять весь этап в одну большую правку.

## Как выбирать проверки

| Изменение | Достаточная проверка во время работы |
| --- | --- |
| Только Markdown-план | Diff, ссылки, согласованность задач и критериев; без запуска приложения |
| Один сценарий сериализации | Тест этого сценария; при изменении общей функции — также compatibility |
| Loader/config/factory | Целевые subprocess-тесты и compatibility |
| Типы | Typecheck потребительских примеров и тесты затронутого runtime, если он менялся |
| Состав npm-пакета/публичные пути | Список содержимого архива и установка архива в изолированный проект |
| Один SSR-бойлерплейт | Его HTTP-проверки, 404/500, закрытие сервера и установка из архива |
| Статический генератор | Выходные файлы, ссылки и ненулевой код при намеренной ошибке страницы |
| Завершение этапа | Один полный набор проверок, определённый в его критериях |

Не повторять уже успешную полную проверку после каждого локального изменения. Повтор нужен после новых затрагивающих её изменений, обнаруженного сбоя или появления конкретного сомнения.

На этапе 1 использовать встроенные node:test и node:assert/strict. Команды npm test и остальные scripts сначала создать в соответствующем шаге; сейчас их нет. Для большого набора файлов предпочитать Node-скрипт со списком аргументов, а не платформозависимые shell-glob.

## Правила надёжности

- Не обновлять ожидаемые снимки HTML только ради зелёного теста. Каждое различие со старым режимом сверить с разрешёнными изменениями в COMPATIBILITY.md.
- Не превращать исключение в пустой HTML, успешную сборку или пропущенный тест.
- Не проверять только код выхода: для SSR проверять ответ, для генерации — содержимое файлов, для публикации — установленный архив.
- Конфигурация и ESM-кэш требуют отдельных процессов. Тесты с разными cwd/env не должны менять глобальное окружение параллельно в одном процессе.
- Временные проекты создавать вне исходного проекта. Устанавливать туда проверяемый архив; не подменять такую проверку npm link.
- Завершать запущенные тестом серверы и дочерние процессы. Удалять только собственные временные каталоги после проверки абсолютного пути.
- Публикуемые примеры не должны зависеть от локальных абсолютных путей, внутренних aliases этого репозитория или установленного рядом исходного checkout.
- Не назначать процент покрытия ради числа: обязательны сценарии ошибок, совместимость, реальные импорты и установка пакета.
- Разделять «не проверено», «проверка завершилась ошибкой» и «проверено успешно».

## Когда нужен более глубокий разбор

Уже зафиксированные шаги исполнять по их входам и ожидаемым результатам. Новый разбор нужен, если для исправления приходится менять старый возвращаемый тип, дефолт, публичный путь, ключ ESM-кэша или диапазон Node.js.

В этом случае подготовить маленький пакет контекста: идентификатор шага, воспроизводящий пример, фактический и ожидаемый результат, затронутый пункт контракта и варианты решения. Записать принятое решение перед дальнейшей реализацией. Не просить подтверждения для обычных правок, уже описанных в плане; уточнение требуется только для нового существенного изменения за его пределами.

Если одна и та же проверка повторно падает по той же причине, вернуться к причине и минимальному примеру. Повторный запуск всей сборки без изменения условий не является прогрессом. Независимые порученные шаги можно продолжать.

Меньший reasoning сам по себе не гарантирует качество. Проверяемые примеры, узкая задача и фиксированный контракт должны давать исполнителю способ обнаружить ошибку, а не только инструкцию «работай аккуратно».

## Карточка передачи работы

В конце рабочего блока обновить карточку в файле текущего этапа:

| Поле | Что записать |
| --- | --- |
| Последний завершённый шаг | Идентификатор и дата |
| Изменённые файлы | Только существенные файлы текущего шага |
| Проверка | Точная команда, версия Node.js/ОС, результат |
| Следующее действие | Один конкретный следующий шаг |
| Ограничения | Непроверенная среда, известный legacy-риск или внешняя зависимость |

Если принято новое решение, добавить краткую запись «причина → решение → влияние на совместимость» рядом с шагом. Не копировать целиком журналы инструментов и не дублировать историю во всех файлах.
