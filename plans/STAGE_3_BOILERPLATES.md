# Этап 3. Бойлерплейты

[Общий план](../PLAN.md) · [Порядок работы](WORKFLOW.md) · [Контракт](COMPATIBILITY.md)

Статус: не начат. Предусловие: завершены этапы 1–2; есть проверенный архив ядра.

Результат: четыре небольших самостоятельных проекта — Minimal, Express SSR, Fastify SSR, Static Site. Каждый можно скопировать отдельно и проверить с выбранной версией jtsx-loader.

Границы: никаких email-шаблонов, SMTP, CMS, авторизации, БД, обязательного Docker, React или генератора npm create. TSX — дополнительный preset, а не четыре отдельных больших проекта.

## S3.1. Общие правила шаблонов

- [ ] Выполнено и проверено.

Создать каталоги templates/minimal, templates/express-ssr, templates/fastify-ssr, templates/static-site. У каждого собственные package.json, README, необходимые scripts и зависимости. Копия не зависит от родительского репозитория или файлов соседнего шаблона.

Зафиксировать общее поведение:

- ESM и запуск с --import jtsx-loader. Не использовать внутренний alias #@ этого репозитория.
- Данные загружаются в entrypoint/обработчике запроса, затем передаются в Page(props). Внутренний HTTP-запрос к самому себе не нужен.
- Рендер вызывается с await. В SSR/SSG можно явно подключать asyncFactory после этапа 1; Minimal показывает простой сценарий без обязательной сложной конфигурации.
- Явно включать escapeAttributes в примерах с динамическими атрибутами. Недоверенный текст выводить через __escape; обработчики custom attributes экранируют значения отдельно.
- В dev перезапуск процесса и наблюдение за JSX/TSX/JS/конфигом; в production обычные импорты без ?reload.
- Статику отдавать только из public. Страницы и server-код в public не помещать.
- Строгую проверку конфига включать через окружение до регистрации loader. Для переносимости использовать небольшой Node launcher с env либо поддерживаемый env-file, а не POSIX-присваивание ENV=value в npm script.
- Зависимости Express/Fastify принадлежат соответствующему шаблону, не runtime ядра. Версии и engines проверяются при создании шаблона и фиксируются lock-файлом.

Сначала определить проверяемый источник ядра. Пока релиз не опубликован, тестовый harness устанавливает подготовленный архив в копию шаблона; README помечает пример как Unreleased и описывает локальную установку архива. Не оставлять в распространяемых package.json локальные пути или номер версии, которой ещё нет в registry.

Проверка: каждый каталог копируется во временную директорию; общие настройки не требуют запуска всех шаблонов одновременно. Отдельно фиксируются состояния «проверен с архивом» и «готов для установки из npm».

## S3.2. Minimal

- [ ] Выполнено и проверено.

Создать один Page.jsx и render.mjs. Команда render получает данные, вызывает await Page(props) и выводит HTML; без HTTP framework, CSS-сборщика и dev-сервиса. Показать передачу props, вложенный синхронный компонент и безопасный вывод текста.

README: установка, одна команда, ожидаемый HTML, версия ядра, Node.js и куда добавлять свои компоненты.

Проверка: процесс выдаёт ожидаемый HTML, заканчивается с кодом 0, не делает сетевых запросов. Ошибка рендера даёт ненулевой код. Нет зависимостей Express/Fastify.

## S3.3. Express SSR

- [ ] Выполнено и проверено.

Создать server/app.js для сборки приложения, отдельный entrypoint запуска, pages, components, layouts и public. Достаточно главной страницы, одной страницы с параметром и 404/500.

Использовать явные маршруты. Статус и Content-Type устанавливаются обработчиком; HTML получается через await Page(props). Обработку ошибки страницы отделить от отсутствия маршрута. Production-ответ 500 не должен содержать исходный stack trace.

Проверка: через локальный сервер на свободном порту проверить HTML, props, статику, 404 с точкой и без точки, 500 и отсутствие доступа к server/pages. Все серверы закрываются после проверки. Изменение JSX в dev появляется после перезапуска.

## S3.4. Fastify SSR

- [ ] Выполнено и проверено.

Сделать структуру и учебный сценарий аналогичными Express SSR, используя native Fastify routes, error handler, not-found handler и reply.type('text/html').send(await Page(props)). Функция buildApp собирает приложение отдельно от listen.

Для ресурсов использовать совместимую версию @fastify/static с корнем public. Не добавлять @fastify/view или второй шаблонизатор только ради вызова функции компонента. При реализации сверить текущие версии Fastify, static plugin и Node.js по официальной документации; engines ядра из-за этого не менять.

Проверка: app.inject для HTML, props, ресурсов, 404/500 и запрета исходников; app.close после тестов. Дополнительно один subprocess smoke запуска опубликованной команды start с настоящим HTTP-запросом: inject сам по себе не проверяет CLI и регистрацию loader.

Основание: Fastify описывает поддержку версий в [LTS](https://fastify.dev/docs/latest/Reference/LTS/), а проверку через inject — в [Testing](https://fastify.dev/docs/latest/Guides/Testing/). Документация просмотрена 2026-09-11; точные версии зависимостей перепроверить перед установкой.

## S3.5. Static Site

- [ ] Выполнено и проверено.

Создать явный список маршрутов, страницы/layouts, public, build.mjs и отдельный preview. Генератор записывает HTML и копирует ресурсы в dist. Вызов сборки не требует работающего SSR-сервера или внешней CMS.

Обрабатывать маршрут до построения пути: результат остаётся внутри dist, duplicate output — ошибка. При сбое страницы сборка завершается ненулевым кодом, старый успешный output не выдаётся за новый. Сначала собирать во временный каталог, затем заменять только проверенный output-каталог текущего шаблона.

Проверка: минимум две страницы и общий layout, ресурсы и локальные ссылки. Искусственная ошибка компонента и конфликт выходных путей завершают сборку ошибкой. Проверка границ пути не изменяет файлы вне временного проекта.

## S3.6. TSX preset и проверка всех копий

- [ ] Выполнено и проверено.

Добавить переиспользуемые TSX-примеры и tsconfig на основе типов этапа 2. Runtime-entrypoints/помощники могут оставаться JS; обещать полноценное выполнение любых .ts нельзя. Preset должен включать typecheck и работать без @ts-nocheck.

Сделать один harness, который копирует выбранный шаблон во временный проект, устанавливает один и тот же проверяемый архив ядра и запускает его команды. Проверить все четыре шаблона в JS и с TSX preset. Во время разработки запускать только изменённый шаблон; все варианты — при завершении этапа.

## S3.7. Подготовить выдачу пользователям

- [ ] Выполнено и проверено.

Создать templates/README.md с таблицей выбора и инструкцией копирования; у каждого шаблона указать проверенную версию ядра, окружение, команды и границы. Не требовать выбора из нескольких неописанных архитектурных альтернатив.

Готовить ZIP из самостоятельной копии без node_modules, .env с секретами и временных результатов. До npm-релиза архивы считаются локальным preview; для внешней выдачи проверить npm-install путь с реально опубликованной версией и удалить временную подмену зависимости на tarball. Публикация ядра не входит автоматически в создание шаблонов.

## Критерии завершения

- [ ] Пройдены S3.1–S3.7; есть ровно четыре предусмотренных назначения без генерации писем.
- [ ] Каждый шаблон запускается отдельно из копии с проверенным архивом; локальный checkout не нужен.
- [ ] Express и Fastify проходят сопоставимые HTTP-сценарии; Fastify проверен также через настоящий start.
- [ ] SSG имеет проверенные ошибки и границы output, Minimal остаётся минимальным.
- [ ] TSX preset работает с реальными типами, .ts-ограничение описано.
- [ ] Указано, готова ли выдача через npm; до выпуска новые API не представлены как опубликованные.
