## S4.1. Основа сайта и единый источник содержимого

- [ ] Выполнено и проверено.

Создать самостоятельный docs-site с собственными devDependencies и scripts. За основу взять подход Static Site из этапа 3; страницы собирать через jtsx-loader. Содержание хранить в Markdown, интерфейс — в layouts/components, ресурсы — в public, результат — в отдельном dist.

Выбранные средства: markdown-it для Markdown и Shiki для подсветки во время сборки. Не переносить эти зависимости в runtime npm-модуля. При установке проверить конкретные версии и engines: требования сборки сайта не должны менять поддержку Node.js у loader.

Примеры кода читать из настоящих исполняемых файлов по стабильным идентификаторам, а не копировать в несколько JSX/Markdown-страниц. Не исполнять произвольные блоки Markdown как серверный код; только заранее выбранные примеры из репозитория.

Проверка: одна Markdown-страница собирается в HTML через layout, включает фрагмент из реального файла и работает через локальный preview. Ошибка чтения обязательного примера останавливает сборку.

Основание: [markdown-it](https://github.com/markdown-it/markdown-it), [Shiki](https://shiki.style/guide/install) и его [интеграция с markdown-it](https://shiki.style/packages/markdown-it) поддерживают выбранный подход. Источники просмотрены 2026-09-11. Shiki рекомендует переиспользовать экземпляр highlighter; не создавать его заново для каждого блока кода.

## S4.2. Подробное содержание

- [ ] Выполнено и проверено.

Подготовить отдельные короткие страницы:

1. Что делает loader, сценарии использования и требования Node.js/ESM.
2. Быстрый старт без framework и отдельные инструкции Express SSR/Fastify SSR.
3. Компоненты, props, layouts, children, Fragment, массивы и условия.
4. Async: явный await в legacy, подключение asyncFactory, порядок children и обработка ошибок.
5. Атрибуты: native HTML, style, className/React mappings, custom attributeParser.
6. Экранирование: __escape, __raw, escapeHtml, escapeAttributes; обычные и уже экранированные данные, ограничения защиты.
7. Конфигурация: каждый ключ, default, пример и поведение при ошибке; отдельное описание JTSX_STRICT_CONFIG.
8. JSX/TSX и типы: рабочий tsconfig, typecheck, отличие от выполнения обычных .ts.
9. Разработка и production: restart, назначение ?reload, ESM-кэш и его ограничения.
10. Статическая генерация, HTTP 404/500, диагностика и частые ошибки запуска.
11. Выбор и скачивание четырёх бойлерплейтов.
12. Обновление версии: контракт совместимости, новые режимы, CHANGELOG и проверенные среды.

Основной новый материал подготовить на русском. Существующие английские вводные страницы сохранить; неполный перевод обозначать прямо. Общие фрагменты кода должны иметь один источник. Не создавать пустые английские страницы с видом завершённого перевода.

Видимо различать текущий npm-релиз и Unreleased-возможности. Инструкция npm install должна вести к реально доступному API; до выпуска показывать отдельный локальный preview/порядок установки архива.

Проверка: у каждого описанного ключа есть соответствующий тест или проверенный пример; дефолты совпадают с кодом. Ни один текст не обещает автоматическое экранирование children или безопасный безграничный ?reload.

## S4.3. Подсветка и проверяемые примеры

- [ ] Выполнено и проверено.

Подключить JSX, TSX, JavaScript, TypeScript, JSON, HTML, CSS, Bash и PowerShell; не загружать весь каталог языков. Подсвечивать при сборке и передавать браузеру готовый HTML. Неизвестный язык показывать экранированным plain text.

Добавить подпись языка/файла, кнопку копирования исходного текста и при необходимости небольшую пару «код → результат». Копирование берёт исходный текст, без HTML-тегов подсветки, номеров строк и лишних символов. Поддержать длинные строки горизонтальным скроллом внутри блока.

Markdown HTML отключён по умолчанию; вставки доверенного сгенерированного HTML контролируются сборкой. Пример, содержащий script, должен отображаться как код и не исполняться от одного открытия документации. Все демонстрационные запросы используют локальные/фиксированные данные, а не доступность чужого API.

Проверка: JSX-теги, кавычки, обратные косые черты и многострочный код сохраняются при отображении/копировании. Выполняемые примеры проверяются отдельной командой; иллюстративные и намеренно ошибочные блоки явно маркируются и имеют ожидаемый результат.

## S4.4. Навигация, поиск и адаптивный интерфейс

- [ ] Выполнено и проверено.

Сделать боковую навигацию, оглавление текущей страницы, устойчивые anchors, предыдущую/следующую страницу и заметную версию документации. Для первого выпуска поиска достаточно статического индекса заголовков/описаний и текстовой фильтрации; отдельный сервер поиска не нужен.

Сайт должен быть удобен на узком экране: мобильное меню, читаемая типографика, код не расширяет всю страницу. Кнопки и меню доступны с клавиатуры; есть заметный focus и понятные названия. Подсветка читается в светлой/тёмной теме, основной текст и код доступны без клиентского JavaScript.

Проверка в настоящем браузере: desktop и узкий экран, переход к anchor, поиск, мобильное меню, копирование, смена темы и клавиатурная навигация. Сохранить найденные проблемы и исправить их до завершения; одних HTTP 200 недостаточно для проверки интерфейса.

## S4.5. Ссылки, старые адреса и артефакт

- [ ] Выполнено и проверено.

Проверять внутренние страницы, anchors, файлы загрузки и ссылки на примеры автоматически. Подготовить title/description, sitemap, robots и страницу 404 с реальным site URL из конфигурации. Не выдумывать lastmod по моменту сборки.

Сохранить назначения старых маршрутов / и /ru из существующего example; изменения других адресов оформлять явной картой переноса. Не считать старые адреса живого сайта проверенными только по исходнику: перед реальной публикацией сверить доступную текущую версию.

Собрать статический архив, проверить его отдельным preview и записать версию ядра/состояние релиза. Скачиваемые бойлерплейты включать как готовые только после проверки их способа установки из S3.7. До этого допустим явно подписанный локальный preview, без обещания готового npm-install пути.

При отдельном поручении на публикацию сначала подготовить и проверить весь артефакт, затем выполнить размещение в согласованной среде и проверить публичные URL. Не менять существующий хостинг только из-за выбора инструментов сборки.

## Критерии завершения

- [ ] Пройдены S4.1–S4.5, все предусмотренные разделы содержат конкретные примеры.
- [ ] Примеры исполняются из одного источника и соответствуют обозначенной версии API.
- [ ] Работают подсветка, копирование, поиск, anchors и мобильная навигация.
- [ ] Проверены desktop/узкий экран/клавиатура, код не исполняется как содержимое страницы.
- [ ] Нет битых внутренних ссылок и скрытых зависимостей от внешнего API при сборке.
- [ ] Старые назначения маршрутов сохранены; версии опубликованных и будущих возможностей не смешаны.
- [ ] Есть проверенный статический артефакт и отдельная запись о публикации: не запрошена/выполнена/не проверена. Локальная готовность не называется публичным размещением.
