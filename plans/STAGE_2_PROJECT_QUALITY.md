# Этап 2. Общее улучшение проекта

[Общий план](../PLAN.md) · [Порядок работы](WORKFLOW.md) · [Контракт](COMPATIBILITY.md)

Статус: не начат. Предусловие: завершён этап 1 и проходят его проверки.

Результат: понятная внутренняя структура, достаточные тесты, типы, CI и проверяемый npm-артефакт. Рефакторинг не меняет HTML или публичные точки входа.

Границы: не добавлять React, клиентский runtime, streaming, новую систему маршрутизации в ядро, обработку писем, новый hot-reload engine или npm-генератор проектов. Не обновлять зависимости все сразу.

## S2.1. Разделить внутренние обязанности

- [ ] Выполнено и проверено.

Читать: loader/loader.mjs, обе фабрики после этапа 1, конфигурацию и их тесты.

Выполнять отдельными маленькими переносами:

1. Общая нормализация настроек и диагностика; сохранить разные контексты выполнения конфига.
2. Отдельная функция transpile(source, options, sourcefile); loader отвечает за URL и протокол hooks.
3. Отдельные функции атрибутов и сборки HTML, переиспользуемые обеими фабриками.
4. Раздельные политики children: legacy сохраняет результаты K2, async-нормализация следует K4. Не «исправлять» старый режим во время переноса.
5. Убрать только доказанно неиспользуемые внутренние части, например AttributeMapper. Не удалять доступные снаружи utils или таблицу атрибутов из-за отсутствия внутренних импортов.

Не создавать класс или дополнительный пакет для каждой функции. Для каждого переноса проверять соответствующий тест и compatibility; весь набор запускать один раз после завершения этой группы.

## S2.2. Систематизировать тесты и команды

- [ ] Выполнено и проверено.

Читать: tests после этапа 1 и package.json.

Действия: выделить группы renderer, loader/config, compatibility, HTTP demo и package installation. Добавить понятные npm scripts: test:renderer, test:loader, test:compat, test:example, test:package. npm test запускает тесты ядра; будущие tests внутри templates/docs-site не должны случайно попадать в его автоматическое обнаружение.

Сделать один небольшой runner со списками тестовых файлов, если он нужен для переносимости. Переиспользовать создание временных проектов и очистку процессов. Не добавлять второй тестовый framework поверх node:test.

Обязательные сценарии: сочетания опций, alias/import resolution, cwd вне пакета, query/hash, .tsx, вложенные async-ошибки, custom attributeParser, сырые и экранированные данные. Проверять числа 0 отдельно от false. Крупные снимки страниц дополнять точными утверждениями о проблемных значениях.

Проверка: каждая команда работает отдельно; полный запуск не дублирует одну группу несколько раз. Намеренный сбой fixture даёт ненулевой код, ошибка не скрывается catch или пропуском теста.

## S2.3. Типы и минимальные средства качества

- [ ] Выполнено и проверено.

Действия:

1. Добавить декларации обоих публичных factory-модулей и конфигурации: реальные возвращаемые типы, children, native HTML/SVG-атрибуты, custom attributeParser.
2. Подключать JSX-типы явно через документированный tsconfig/preset. Не добавлять глобальный JSX всем пользователям при обычном импорте пакета: рядом могут быть другие JSX-системы.
3. Добавить маленький потребительский TSX-проект для typecheck. Проверить рабочий код и намеренно неверные типы без any/@ts-nocheck, скрывающих проблему.
4. Удалить @ts-nocheck из демонстрационных TSX после исправления типов Props. Не добавлять загрузку обычных .ts/.mts/.cts в качестве побочного эффекта.
5. Добавить минимальный lint для исходников ядра и проверку синтаксиса; команды должны работать на выбранной среде разработки. Не форматировать весь репозиторий ради одного правила.

Runtime-примеры могут использовать JS-entrypoint и TSX-шаблоны; .ts-файл с исполняемым кодом не становится поддерживаемым автоматически. Typecheck выполняет TypeScript, esbuild только транспилирует.

Проверка: типы доступны из установленного архива, работают ESM и выбранный JSX preset, ошибки типов действительно обнаруживаются. Runtime-совместимость проверяется отдельно от typecheck.

## S2.4. CI и состав публикуемого пакета

- [ ] Выполнено и проверено.

Действия:

1. Добавить CI: тесты ядра, typecheck, lint и test:package. Изменения только планов не требуют всей runtime-матрицы.
2. Проверять минимум Node.js 20.16.0 и основные разрешённые линии 22/24 на Linux/Windows. Перед выпуском проверить также последние версии линий 20/21/23, пока они входят в engines. Не сокращать engines из-за отсутствия локального установленного Node.
3. Для экономии обычный PR проверяет основные среды; расширенная матрица запускается для выпуска и изменений loader/совместимости. В отчёте перечислять проверенные версии, а не обещать все patch-версии диапазона.
4. Добавить явные правила включения файлов в npm-пакет. Сравнить с исходным списком из 23 файлов: runtime, новые типы и прежние пути сохраняются. Новые планы, внутренние тесты, шаблоны и сайт не обязаны поставляться с ядром.
5. Проверить отсутствие .env, временных проектов, build-артефактов и секретов. Не вводить ограниченный exports в этом этапе.
6. Подготовить release-check: проверки → архив → установка в чистый проект → отчёт. Существующий npm run patch повышает версию и публикует; не использовать его как команду проверки.

Проверка архива должна устанавливать обычные зависимости, а не брать esbuild из соседнего checkout. Кэш npm можно направить в разрешённый временный каталог. Ограничение сети отмечать как непроведённую установку, а не успешную проверку.

## S2.5. Проверить производительность без изменения семантики

- [ ] Выполнено и проверено.

Действия: сделать один небольшой воспроизводимый benchmark холодного импорта, повторного рендера и ?reload. Сохранять версии Node, число итераций и сценарий. Не устанавливать универсальный лимит по измерению одного компьютера.

Сначала измерить; отдельный кэш transpile добавлять только при подтверждённой пользе, с учётом исходника/опций/sourcefile. Такой кэш не освобождает записи ESM от ?reload. Не заменять transformSync на async по предположению, что он блокирует основной поток приложения: loader hooks выполняются отдельно.

Проверка: корректность выхода совпадает; при отсутствии доказанной пользы достаточно результатов измерения и сохранения простой реализации. Новый worker reload вынесен за границы плана.
